## 2026-08-11 — OTA Hub flash-capacity analysis

- The copied target is [`firmware/hub-ota/`](firmware/hub-ota/); the original [`firmware/hub/`](firmware/hub/) was not edited for this request.
- Arduino-ESP32's active default 4 MiB partition table provides two 0x140000-byte (1.25 MiB) OTA app slots and a 0x160000-byte (1.375 MiB) SPIFFS/LittleFS region. The OTA-enabled Hub image is 955,125 bytes, or 72.9% of either default app slot.
- Exact project-owned/deployed files under [`firmware/hub-ota/data/`](firmware/hub-ota/data/) total 308,483 bytes. The largest asset is the offline decoder [`jsQR.js`](firmware/hub-ota/data/js/vendor/jsQR.js) at 256,885 bytes.
- Built-in `min_spiffs` is unsuitable because its filesystem cannot hold the current web bundle. Built-in `huge_app`/`no_ota` layouts are unsuitable because they remove the two-image OTA update model. A project-specific table is therefore the correct optimization, not arbitrary use of the largest app partition.

- Application capacity failure is deterministic: PlatformIO/OTA rejects an image that does not fit the inactive app slot. It does not intentionally install half an image. Filesystem pressure is also checked: scratch open/write, byte-count, JPEG markers, and final commit must all succeed before image state is published; failure returns an HTTP error and discards scratch.
- Dual slots protect the running image from an interrupted transfer because ArduinoOTA writes the inactive slot before selecting it. Automatic rollback after a valid new image boots and later fails is not claimed; that would require an additional ESP-IDF rollback/health-confirmation policy.
- Changing partition geometry still requires one USB deployment because an already-running image cannot safely redefine its own flash map over OTA. The documented first deployment is erase → USB firmware upload → LittleFS upload; later firmware builds use authenticated `espota` to `192.168.4.1:8266`.

### Shared ESP-NOW contract

- The active shared packet in [`firmware/common/MuseumProtocol.h`](firmware/common/MuseumProtocol.h:36) is a packed 24-byte fixed-width `MuseumMessage`: magic `0x4D53`, protocol version 1, type/node/station/flags, fixed-point health fields, visitor count, 16-bit sequence, 32-bit uptime, and a final 16-bit additive checksum. All ESP-NOW members are fixed to channel 1 and broadcast address `FF:FF:FF:FF:FF:FF`.

### Camera node — code-authoritative inventory

- Hardware/configuration: classic ESP32-CAM profile with PSRAM; GC2145 DVP sensor on the AI-Thinker pin map; 10 MHz XCLK; RGB565; QVGA 320×240; one framebuffer; two stale-frame flushes separated by 40 ms; software JPEG quality 15. The GC2145 has no native JPEG path.
- Camera DVP consumes GPIO0/5/18/19/21/22/23/25/26/27/32/34/35/36/39. Optional SD_MMC deliberately uses one-bit mode on GPIO2/14/15, leaving GPIO4 for the normally-off flash LED and GPIO13 for the robot link.
- Active trigger edge: robot GPIO14 software TX → camera GPIO13 hardware UART1 RX, 9600 baud, 8N1, newline-delimited `SHOOT <station>`, one-way, shared ground. USB Serial at 115200 is an independent command source with its own bounded 96-byte buffer; the two streams cannot splice partial lines together.
- State owned in RAM: camera/SD readiness, detected PID/card type/flash state, last JPEG pointer+length, optional last SD path, last station, and auto-capture interval/timestamp. The last RAM JPEG is replaced only after a new conversion succeeds and supports `SEND` retry; it is lost on reset.
- Capture pipeline: reject when camera uninitialized → flush stale frames → acquire RGB565 → `frame2jpg()` → return camera framebuffer → replace retained RAM JPEG → optionally save+flush+reopen-size-verify `/photos/IMG_####.JPG` on SD → if Wi-Fi is already connected, upload multipart JPEG → on HTTP 200, broadcast `MSG_IMAGE_READY` best-effort. A successful capture does not depend on SD.
- SD persistence: SD is **not mounted at boot** in current source despite the README's capture-to-SD emphasis; boot explicitly says to run `INIT`. When mounted, each save rescans `/photos` for the largest `IMG_####.JPG` and uses +1, so filenames survive reboot without an index file. There is no pruning or wrap/collision policy beyond the 16-bit parsed index and formatted four-digit name.
- Network edge: camera joins `MuseumHub` / `museum2026` as STA (15 s join timeout), then posts to `http://192.168.4.1/api/image/upload?station=N` using multipart field `image`, MIME `image/jpeg`, and an 8 s HTTP timeout. The full multipart body is allocated contiguously in PSRAM/heap. HTTP 200 alone controls success.
- `SHOOT` first requires Hub Wi-Fi; if join fails, **it does not capture at all**, despite the README statement that the photo remains SD-only when the Hub is unreachable. `CAPTURE`, by contrast, captures regardless of connectivity and uploads only if already connected. This distinction is architecturally important because the robot uses `SHOOT`, not `CAPTURE`.
- ESP-NOW on camera is send-only and initialized best-effort after the Wi-Fi join attempt. It uses the current STA channel and sends `MSG_IMAGE_READY` with node ID 10 after a successful HTTP upload. Current Hub source ignores `MSG_IMAGE_READY`, so this packet is an **implemented transmitter with no active consumer** and does not actually accelerate dashboard refresh.
- Failure fallbacks: camera-init failure leaves commands alive for `INIT`; SD failure degrades to RAM+HTTP; `CAPTURE` while offline retains the new JPEG for later `WIFI` + `SEND`; HTTP/allocation failures preserve the RAM JPEG; flash never fires automatically to reduce brownout risk. Wi-Fi reconnect is blocking up to 15 s only when explicitly needed by `SHOOT`, `SEND`, or `WIFI`.
- Concurrency: camera uses the default Arduino `setup()`/single `loop()` model. Capture, Wi-Fi join, JPEG conversion, and HTTP upload are synchronous/blocking; only command polling and auto timing are cooperative between operations. There is no dedicated FreeRTOS task.

### Hub node — runtime, server, emergency, and gallery architecture

- Hardware/network authority from [`config.h`](firmware/hub/include/config.h): the Hub ESP32 owns the `MuseumHub` / `museum2026` channel-1 SoftAP at `192.168.4.1`, seven WS2812 station pixels on GPIO15, a passive buzzer on GPIO4, a HIGH-when-pressed emergency input on GPIO21 with internal pull-down, and optional VSPI microSD on SCK18/MISO19/MOSI23/CS5 at 4 MHz. Static UI assets always live in LittleFS even when gallery photos use SD.
- Boot order in [`setup()`](firmware/hub/src/main.cpp:833) is serial → pixels/buzzer/button/random seed → mutex → LittleFS → gallery backend recovery/pruning → legacy-image cleanup → fixed-IP SoftAP → wildcard DNS → 16-entry ESP-NOW queue and unencrypted AP-interface broadcast peer → HTTP routes/custom multipart handler → server → 16 KB web task pinned to Core 0. The Arduino [`loop()`](firmware/hub/src/main.cpp:918) remains on Core 1.
- Core ownership is explicit: [`webTask()`](firmware/hub/src/main.cpp:657) cooperatively services DNS and HTTP on Core 0; the Wi-Fi receive callback validates exact 24-byte packets and non-blockingly queues them; Core 1 drains that queue, settles robot motion, synchronizes emergency state, debounces the button, advances the siren, transmits emergency state, renders LEDs, and yields about 5 ms. [`gState`](firmware/hub/include/MuseumState.h:16) is the only cross-core model and is protected by one FreeRTOS mutex; [`gPhotos`](firmware/hub/src/main.cpp:35) is intentionally Core-0-only.
- Hub receive behavior is narrower than the shared vocabulary: [`processMessage()`](firmware/hub/src/main.cpp:172) consumes LOCATION, EMERGENCY, and HEALTH only. VISITOR_COUNT, IMAGE_READY, COMMAND, and HEARTBEAT are ignored. Packets have no sender-MAC/node allowlist, sequence freshness test, replay rejection, acknowledgement, or queue-overflow report.
- LOCATION maps station IDs 1–7 to configured names, copies the moving flag, and refreshes a timestamp; [`settleRobotMotion()`](firmware/hub/src/main.cpp:911) forces moving false after 2.5 s without refresh. Because the current robot target sends no LOCATION packet, this is an implemented Hub receiver with no active robot sender; only the unauthenticated local `/api/robot/advance` simulator currently changes Hub robot position in the five-project combination.
- Emergency is Hub-owned shared state. A dashboard POST, valid incoming EMERGENCY packet, or physical button transition changes the same Boolean. A short debounced press raises it; holding the button for 3 s clears it. [`syncAlarmFromState()`](firmware/hub/src/main.cpp:749) also makes dashboard/radio clear stop `tone()` immediately.
- [`pumpEmergencyBroadcast()`](firmware/hub/src/main.cpp:226) is the Hub's only active ESP-NOW transmitter: every transition sends immediately and initiates the configured six-frame transition burst at 60 ms spacing, then the current state is rebroadcast every 2 s. Packets are channel-1 broadcast, unencrypted, use Hub node ID 10, increment a RAM-only 16-bit sequence, and carry uptime. The robot actively consumes this packet; the camera does not.
- Emergency outputs are non-blocking: the passive buzzer alternates 600/1200 Hz every 400 ms, while all seven pixels blink red at roughly 250 ms toggles. Outside emergency, only the known current-station pixel lights—blue while moving, green while not moving; unknown/no station leaves all pixels dark.
- Shared RAM state includes robot state, emergency, up to eight health rows, up to 24 drop-oldest visitor requests, cumulative approval count, and latest-image metadata. Visitor/check-in/health/robot state is not persisted. Approval count is cumulative rather than occupancy; denial after approval does not decrement it, and missing IDs still receive `{ok:true}` from approve/deny handlers.
- Browser/API surface in [`setup()`](firmware/hub/src/main.cpp:883): `GET /api/state`, `POST /api/checkin`, `GET /api/enter`, `GET /api/request`, `POST /api/approve`, `POST /api/deny`, `POST /api/emergency`, `POST /api/robot/advance`, multipart `POST /api/image/upload`, `GET /api/image`, `GET /api/gallery`, and `POST /api/gallery/clear`. No route has authentication or authorization; every associated control is available to any SoftAP client.
- Camera ingestion accepts only multipart field `image` with exact MIME `image/jpeg`; raw POST receives 415. Upload chunks stream to LittleFS `/upload.tmp` with a 65,535-byte ceiling, then completion verifies received-versus-saved size and JPEG SOI/EOI before committing. This is framing/completeness validation, not a full JPEG decode. A failed upload removes scratch and preserves the previous newest image.
- [`PhotoStore`](firmware/hub/src/PhotoStore.cpp) tries SD three times and falls back to LittleFS, rebuilds a newest-first maximum-32-entry RAM index, and enforces the configured 12-photo gallery. Actual filenames are strict 8.3 such as `/photos/I00012S3.JPG`; comments/README examples using `IMG_<seq>_S<station>.JPG` are stale. Even for an SD gallery, multipart chunks stage in LittleFS and are copied to SD once at commit.
- Gallery sequence state is persisted in `/photos/SEQ.TXT`; normal clear deletes photos but deliberately retains the issued-sequence floor so immutable `/api/image?seq=N` URLs are not reused. At the hard ceiling 65,000, source wipes the gallery and resets the sequence, an exceptional eventual violation of the never-reuse cache invariant. Eviction occurs before a new final copy, so a later commit failure can leave the gallery down one older photo.
- Static files are served from LittleFS with no-cache headers. Wildcard DNS points every hostname to the Hub, but only recognized OS captive-probe paths redirect to `/`; arbitrary missing files return 404. Per-sequence images receive one-year immutable caching, whereas newest-image, gallery, state, and deployed app files are uncached.
- Source/README reconciliation: dual-core split, emergency timer, passive-buzzer behavior, multipart upload, SD→LittleFS fallback, and 12-photo retention are implemented. Claimed robot LOCATION heartbeat is not implemented by the current robot; camera IMAGE_READY has no Hub consumer; and documented long gallery filenames differ from strict runtime names. These must be shown as inactive/drift notes, not active connectors.

- A source-only search across the five targets reconfirms exactly two ESP-NOW send sites: Hub [`broadcastEmergency()`](firmware/hub/src/main.cpp:208) sends EMERGENCY, and camera [`notifyHubImageReady()`](firmware/cam/src/main.cpp:518) sends IMAGE_READY. ### End-to-end normal-tour event flow

1. Safe startup is distributed but conservative: Nano boots into active hard brake; robot then sends `STOP` and `GET`, starts with its tour stop latch set, and will not move until the START card/audio path succeeds. Camera and Hub boot independently; neither is required for Nano's safe state.
2. MFRC522 reads and halts a card. Unknown UIDs only log; a repeated identical UID inside 1.5 s is ignored. START UID clears the stop latch, sends Nano `STOP`, plays track 1, and sends Nano `START` only after a valid DFPlayer completion at least 1.5 s after start.
3. Each station UID maps tracks 2–8 to station IDs 1–7. Robot sends Nano `STOP`, starts narration, and schedules one camera command for two seconds later. The timer is non-blocking and fires only while narration remains active; completion/error/timeout/emergency/end/start cancellation prevents a late shot after motion might resume.
4. At the deadline robot sends `SHOOT N` one-way. Camera may block up to 15 s joining `MuseumHub`; if it cannot join, no frame is captured. If joined, it captures RGB565, software-encodes JPEG, retains it in RAM, optionally writes camera-local SD, then performs multipart HTTP upload.
5. Hub streams upload chunks into LittleFS scratch, validates size and SOI/EOI, commits into the 12-image SD/LittleFS gallery, updates mutex-protected latest metadata, and replies HTTP 200. Camera then best-effort broadcasts IMAGE_READY, but Hub ignores it. Admin polling discovers the changed newest sequence within about 1.5 s and fetches the gallery/images.
6. Independently, DFPlayer completion causes robot to cancel any still-pending shot and send Nano `START` if the latch remains clear. DFPlayer unavailable/error or 90 s timeout leaves Nano stopped. END UID stops playback, cancels photography, sends Nano `STOP`, and latches the tour stopped until START.
7. The normal flow contains no robot→Hub station update and no robot→Mega display update. Hub station LEDs and visitor/admin robot cards therefore do not follow physical tour movement unless the admin's local simulation endpoint is used; the display remains outside the runtime path.

### End-to-end emergency event flow

1. Emergency can originate from Hub's physical GPIO21 button, unauthenticated admin POST, or any checksum-valid broadcast EMERGENCY packet. Hub adopts the Boolean, mirrors siren/LED outputs, and marks outbound state dirty.
2. Core 1 broadcasts immediately, repeats a six-frame transition burst at 60 ms gaps, then rebroadcasts every 2 s. Robot callback validates packet shape/checksum and stores only the requested Boolean; the main loop applies the transition before RFID or audio completion handling.
3. On raise, robot cancels pending photography, stops narration/DFPlayer, clears its normal stop latch, and commands Nano `START`. Every mapped card—including START/stations—is ignored except END; the robot therefore drives toward the physical END card without station stops or photos.
4. END during emergency commands Nano hard brake, sets the normal stop latch, and marks emergency end reached. Hub remains in emergency: LEDs continue red blink, buzzer continues two-tone wail, browser banners remain active, and the robot ignores other cards.
5. Clearing by three-second button hold, admin POST, or accepted radio state makes Hub stop the siren and broadcast false. Robot responds by stopping audio/photo activity, commanding Nano `STOP`, and latching stopped. A fresh START card is mandatory before normal movement resumes.
6. Failure boundary: ESP-NOW is unauthenticated broadcast without acknowledgements or sender/sequence checks. Transition bursts reduce packet-loss exposure, and periodic state repairs late/rebooted listeners, but channel mismatch/ESP-NOW init failure/continuous interference can prevent robot evacuation behavior with no end-to-end confirmation at Hub.

### Safety and failure-fallback summary

- **Motion:** Nano's boot state and robot reboot command are both hard brake; unknown/malformed Nano lines do not move it. Tour movement requires recognized START. Audio failure/timeouts stop rather than resume. Emergency intentionally reverses the normal safety choice by commanding forward evacuation until END; no obstacle/position sensor or command acknowledgement protects this run.
- **Photography:** pending trigger is cancelled whenever narration no longer proves the rail is stopped. Camera retains the last good RAM JPEG across capture/upload failures until reset; optional SD adds local persistence. Robot-triggered `SHOOT` has no offline capture fallback because Hub Wi-Fi is checked first.
- **Storage:** Hub falls from SD to LittleFS and recovers valid gallery files at boot. Upload staging plus JPEG marker/size checks preserve prior newest image on most failures, but pre-commit eviction can lose one old photo. Static UI depends on LittleFS even when gallery SD is healthy.
- **Emergency transport:** transition burst and periodic rebroadcast provide eventual-state repair but not delivery proof. Any valid-looking broadcaster can raise or clear state, and robot cannot authenticate the Hub. A Hub reboot resets emergency false and begins broadcasting false unless the physical/button/dashboard/external-radio state is raised again.
- **Web/control:** Hub and robot APIs are unauthenticated on password-protected SoftAPs; passwords are compiled plaintext and identical. Browser failures are mostly silent/stale. Hub upload checks MIME, size, and JPEG edge markers but not image decode; check-in approval is a UI workflow rather than route-level access control.
- **Display:** no active sender means display state cannot affect safety and cannot communicate emergency. A standalone Mega can show EMERGENCY only when manually commanded over USB/Serial1.

## 2026-08-10 — Rail motor-speed field controls

- The requested Motor L/R implementation is currently localized in `ESP32_RFID_MP3_RAIL/ControlPage.h`, `ESP32_RFID_MP3_RAIL/ESP32_RFID_MP3.ino`, and `ESP32_RFID_MP3_RAIL/README.md`; it uses the Nano's existing `SET ML`, `SET MR`, `GET`, and `SAVE` commands rather than changing Nano product code.
- Current Git state also contains concurrent modifications in `ESP32_RFID_MP3_RAIL/platformio.ini`, the three root planning files, and shared/compatibility header moves and copies. Those are not part of the pending synchronization fix and must be preserved without staging, reverting, or rewriting them.
- Remaining known logic defect: a boot-time `GET` can report EEPROM values different from the ESP32's compiled defaults. That unsolicited/initial confirmation must update displayed state without creating a pending request; requested-value comparison is valid only while a web motor command is already pending.
- The synchronization defect is fixed: valid Nano `TUNE` replies always replace the displayed confirmed pair; pending state is cleared only when an existing pending request exactly matches that pair. Unsolicited/startup reports cannot create a pending request.
- Validation exposed nondeterministic generated-artifact interference: one build missed a framework object, then a clean build reported a missing `firmware.elf` even though complete ELF/map/bin artifacts appeared immediately afterward. `platformio.ini` contains no cleanup/build hook and a process inspection found no surviving PlatformIO/SCons job. Continue with serialized (`-j 1`) validation rather than treating these as C++ failures.
- Serialized builds pass for both configured boards: ESP32 uses 50,356 B RAM (15.4%) and 852,789 B application flash (65.1%); Nano uses 282 B RAM (13.8%) and 4,092 B flash (13.3%).
- The embedded console exposes independent Motor L/channel A and Motor R/channel B sliders over 0–255, posts both values to `/api/motors` or `/api/motors/save`, and renders Nano-confirmed/pending/running state from `/api/state`. The companion Nano source contains the matching `SET`, `GET`, and `SAVE` dispatch plus `TUNE ML=n MR=n` reporting and live retuning while driving.
- ESP32 request handling validates both `ml` and `mr` completely before sending any UART command. A valid request stores the desired pair, marks it pending, sends `SET ML`, `SET MR`, then `GET`; the save route appends `SAVE`, so Nano UART ordering persists the final pair. Endpoint responses are HTTP 202 and explicitly represent requested/pending—not confirmed—values.

## 2026-08-10 — Hub firmware flow audit (in progress)

- The Hub is configured as a channel-1 SoftAP at `192.168.4.1` (`MuseumHub` / `museum2026`) and uses that same radio/channel for ESP-NOW. Local outputs are WS2812 on GPIO15, passive-buzzer siren on GPIO4, and a HIGH-when-pressed emergency input on GPIO21.
- Emergency is designed as Hub-owned state: immediate broadcast on transition plus an unconditional state rebroadcast every 2,000 ms. The configured sender node ID is 10.
- Robot movement has a 2,500 ms settle window. A current location/moving report refreshes the timestamp; absent refreshes are expected to make the Hub show a stationary/narrating state after that window.
- Camera storage is configured to try VSPI microSD first (SCK18/MISO19/MOSI23/CS5 at 4 MHz), then fall back to LittleFS, retaining at most 12 photos under `/photos`.
- `MuseumState` is the cross-core RAM model guarded by one FreeRTOS mutex. It contains robot station/motion/timestamp, emergency, up to 8 health rows, up to 24 check-in records, cumulative approvals, and newest-image metadata. The image byte count is only 16-bit, so source inspection must confirm the upload limit is no greater than 65,535 bytes.
- Check-in status is encoded as 0 pending / 1 approved / 2 denied. Request state and counts are RAM-resident and therefore reset on reboot unless later source reveals persistence.
- `PhotoStore` is single-threaded by contract and is used only by the Core-0 web task. At boot it attempts the SD card three times, then falls back to LittleFS; it creates `/photos`, removes any interrupted upload scratch, reconstructs a newest-first RAM index from strict 8.3 names (`I00012S3.JPG`), prunes older valid photos, and reads a persistent `SEQ.TXT` sequence floor.
- Incoming JPEG chunks are deliberately written to the LittleFS scratch `/upload.tmp` even when the final gallery is on SD. At commit, a validated scratch is renamed on LittleFS or copied once to SD, the oldest indexed photo is evicted at the configured limit, metadata is inserted newest-first, and the sequence floor is persisted. This avoids SPI writes inside the HTTP parser callback.
- Clearing the gallery deletes images but deliberately preserves the highest issued sequence. This is required because `/api/image?seq=N` is intended to be immutable-cacheable; reusing a cleared sequence could make browsers display stale pixels.
- Filename comments in `PhotoStore.h` and the Hub README still describe `IMG_<seq>_S<station>.JPG`, but actual source writes strict 8.3 names such as `/photos/I00012S3.JPG`. This is a documentation mismatch, not a runtime-path ambiguity.
- The source enforces a sequence ceiling of 65,000 by wiping the indexed gallery and resetting to sequence 1. That exceptional behavior technically violates the otherwise stated never-reuse/cache invariant after 65,000 accepted captures, although it is declared unreachable in a demo.
- Boot order in actual source is: initialize serial/LED/buzzer/button/random/mutex; mount LittleFS; initialize the photo backend and recover/prune the gallery; remove legacy `/last.*` images; start the fixed-IP SoftAP and wildcard captive DNS; create a 16-message ESP-NOW queue and register an unencrypted broadcast peer; register HTTP routes and the custom multipart handler; start the server; then create a 16 KB web task pinned to Core 0. Arduino `loop()` remains on Core 1.
- ESP-NOW receive callbacks do only fixed-size validation and a non-blocking queue send. Core 1 drains the queue and handles only LOCATION, EMERGENCY, and HEALTH. Other declared protocol types (visitor count, image-ready, command, heartbeat) are ignored. Queue-full drops are silent, packet sequence numbers are ignored, and sender MAC/node authorization is not checked.
- LOCATION maps numeric station `1..7` to the configured string, copies the moving flag, and refreshes `robotMs`; Core 1 clears `robotMoving` 2.5 s after the last moving report. HEALTH upserts by station string into at most 8 RAM rows. EMERGENCY adopts the incoming flag and marks outbound state dirty only on a transition.
- Core 1 loop order is deterministic: drain all queued messages; settle motion; adopt external emergency state into local siren state; debounce/read button; apply press/3 s hold logic; update two-tone siren; send emergency if dirty or 2 s elapsed; render LEDs; sleep about 5 ms. A changed emergency is therefore normally relayed during the same Core-1 pass.
- A short debounced button press latches emergency ON. Holding continuously for 3 s clears it. Dashboard or incoming ESP-NOW changes are mirrored into the local alarm; clearing externally explicitly calls `noTone()`. Emergency LEDs blink all seven red at ~250 ms toggles; normal mode lights only the current station, blue while moving and green otherwise.
- `stateJson()` labels every non-moving state `"narrating"`, including boot with no station/robot packet. It exposes no staleness or online status. Approved count is cumulative and is not occupancy: deny-after-approve does not decrement it, there is no exit handling, and `MSG_VISITOR_COUNT` is ignored.
- Visitor check-ins create short pseudo-random RAM IDs, with a 24-record drop-oldest buffer. Approve/deny return `{ok:true}` even for missing IDs. All API routes are unauthenticated; any client on the AP can approve/deny, toggle emergency, advance the mock robot, clear the gallery, or upload an image.
- Emergency HTTP updates Hub state and schedules an ESP-NOW broadcast; the robot-advance endpoint is only a local simulation and sends no robot command. The Hub's only outbound ESP-NOW packet in this source is the periodic/dirty emergency-state broadcast.
- The upload endpoint intentionally accepts only multipart POST field `image` with exact MIME `image/jpeg`; raw senders get HTTP 415. Chunks stream to LittleFS with a 65,535-byte cap, then completion validates saved byte count plus JPEG SOI/EOI before committing and updating shared image metadata. This validates framing/completeness, not full JPEG decode.
- Static files always come from LittleFS (even if photos use SD), with no-cache headers. Wildcard DNS resolves every hostname to the Hub; recognized OS captive-probe paths redirect to `/`, while arbitrary missing paths return 404.
- The shared protocol packet is packed and checksum-validated with magic/version and a 16-bit additive checksum. This detects ordinary corruption but offers no authentication or replay protection; ESP-NOW broadcast peer encryption is explicitly disabled.
- The deployed browser adapter selects real mode only when the page hostname is exactly `192.168.4.1`; any captive-portal alias/other hostname uses the localStorage mock even though it may be served by the Hub. In normal documented use via the IP, each page subscription creates a 1.5 s `/api/state` poll and silently retains stale cache on errors.
- Browser admin commands are fire-and-forget POSTs, so the page does not inspect HTTP status or server JSON and waits for later polling. Immediate calls to `refresh()` therefore often redraw old cached state first; this is cosmetic, not a duplicate command.
- The gallery client is efficient by design: `/api/state` carries only newest image metadata; `/api/gallery` is fetched initially and whenever newest sequence changes; each `/api/image?seq=N` URL is stable and browser-cacheable. Clear is optimistic in the browser and followed by a delayed gallery refresh.
- The admin source still says health rows are mock values even though real Hub mode renders ESP-NOW HEALTH messages. Unknown/missing robot or health station IDs fall back visually to artifact 1 (`jamdani`), reinforcing the misleading offline-as-valid behavior.
- The UI interpolates request IDs and sensor/content values into `innerHTML`/inline handlers. Current Hub-generated request IDs and configured station strings are constrained, but the pattern is not safe for future untrusted fields.

- The locally available pictured 74HCT125 DIP-14 is accepted and locked for both WS2812B interfaces. When powered at 5 V, its TTL-compatible input threshold accepts an ESP32 3.3 V HIGH and its push-pull output supplies a strong 5 V waveform. Use one enabled channel plus a 330–470 ohm series resistor; place a 100 nF decoupling capacitor at the IC; tie unused buffer inputs to a defined level and disable their active-low output-enable pins HIGH.

## 2026-08-10 — Hub 74HCT125 / WS2812B Wiring Recheck

- Rechecked the active Hub configuration and implementation: NeoPixel data is GPIO15, and the current firmware allocates only `STATION_COUNT = 7` pixels. This differs from the later hardware plan for seven eight-pixel boards (56 pixels), so the physical DIN/DOUT chain is valid but the current image will address only pixel indexes 0–6 until the allocation/rendering logic is expanded to 56.
- The project’s exact standard DIP-14 channel-1 wiring is electrically consistent with the official Nexperia/TI descriptions of the 74HCT125 as four non-inverting buffers with active-low output enables and TTL-compatible inputs. At 5 V, ESP32 3.3 V GPIO15 goes to pin 2 (`1A`), enabled pin 1 (`/1OE`) goes to GND, and pin 3 (`1Y`) drives only the first WS2812B board’s DIN through 330–470 ohms.
- The LED data path is directional: buffer pin 3 -> board 1 DIN; each board DOUT -> the following board DIN; the final board DOUT intentionally remains unconnected. LED 5 V and GND are distributed in parallel, and ESP32, 74HCT125, LED supply, and every LED board must share ground.
- Standard DIP-14 support wiring remains: pin 14 to regulated 5 V, pin 7 to common GND, and 100 nF ceramic directly across pins 14/7. Unused channels are disabled by tying `/OE` pins 4/10/13 HIGH to 5 V, their inputs 5/9/12 LOW to GND, and leaving outputs 6/8/11 unconnected.
- Official-source lookup used Nexperia’s 74HC/HCT125 datasheet and TI’s SNx4HCT125 datasheet search result. Nexperia states that HIGH on `nOE` puts the corresponding output in high impedance; TI identifies TTL-compatible inputs and the non-inverting `Y = A` function. The HCT suffix matters; a plain HC125 at 5 V is not the same guaranteed 3.3 V-to-5 V interface.

### GC2145 caveat (critical)
- The GC2145 **cannot output native JPEG**. Standard `PIXFORMAT_JPEG` / OV2640 CameraWebServer examples fail with `Camera probe failed with error 0x106` / `Detected camera not supported`. The implemented firmware therefore captures **RGB565** and converts each frame to JPEG **in software** with `frame2jpg()` (`img_converters.h`).
- Proven-stable settings (matching the PDF): **XCLK 10 MHz**, `PIXFORMAT_RGB565`, **QVGA 320×240**, **1 framebuffer in PSRAM**. At JPEG quality 15 each QVGA frame encodes to ~1.8 KB.

### Pin map (AI-Thinker / ESP32S-CAM, verified working)
- PWDN 32, RESET -1, XCLK 0, SIOD 26, SIOC 27, Y9 35, Y8 34, Y7 39, Y6 36, Y5 21, Y4 19, Y3 18, Y2 5, VSYNC 25, HREF 23, PCLK 22. Identical to the AI-Thinker pin map that already produced PID 0x2145 in the PDF.

### SD_MMC 1-bit mode (no pin conflicts)
- SD_MMC runs in **1-bit mode** → uses only **GPIO2 (D0) / GPIO14 (CLK) / GPIO15 (CMD)**. The camera DVP bus (5/18/19/21/22/23/25/26/27/32/34/35/36/39) is completely disjoint, and **GPIO4 (onboard flash LED)** stays free. 4-bit SD mode (which would also take GPIO4/12/13) is intentionally NOT used, so the flash LED does not conflict with the card.
- Verified on an 8 GB FAT32 SDHC card: `microSD : mounted /sdcard (1-bit) type=SDHC/SDXC card=7620.0 MB fsTotal=7604.1 MB fsFree=7602.0 MB`.
